==== Phase 1: Minimal Working Broadway {plus} LocalStack SQS Pipeline

We’ll create a tiny Mix project that: - Connects to LocalStack’s SQS -
Uses `broadway++_++sqs` with long polling and batching - Processes
messages (just logs {plus} fake work) - Runs under supervision

This will get you a working end-to-end flow in ++<++ 15 minutes.

===== Step 1: Create the project

[source,bash]
----
mix new sqs_processor --sup
cd sqs_processor
----

===== Step 2: Add dependencies (mix.exs)

[source,elixir]
----
defp deps do
  [
    {:broadway, "~> 1.0"},
    {:broadway_sqs, "~> 0.8"},
    {:ex_aws, "~> 2.5"},
    {:ex_aws_sqs, "~> 3.0"},
    {:jason, "~> 1.4"},
    {:hackney, "~> 1.20"},  # HTTP client used by ex_aws
    {:telemetry_metrics, "~> 1.0"},  # optional, for later metrics
    {:telemetry_poller, "~> 1.1"}
  ]
end
----

Then run:

[source,bash]
----
mix deps.get
----

===== Step 3: Configure for LocalStack (config/dev.exs)

[source,elixir]
----
import Config

config :ex_aws,
  access_key_id: "test",
  secret_access_key: "test",
  region: "us-east-1"

config :ex_aws_sqs,
  scheme: "http://",
  host: "localhost",
  port: 4566
----

LocalStack’s SQS endpoint is `http://localhost:4566` by default.

===== Step 4: Create the Broadway module (lib/sqs++_++processor/processor.ex)

[source,elixir]
----
defmodule SqsProcessor.Processor do
  use Broadway

  alias Broadway.Message

  def start_link(_opts) do
    Broadway.start_link(__MODULE__,
      name: __MODULE__,
      producer: [
        module: {BroadwaySQS.Producer,
          queue_url: "http://localhost:4566/000000000000/my-test-queue",
          config: [
            receive_interval: 1000,  # fallback if no long polling
            wait_time_seconds: 20    # long polling!
          ]},
        concurrency: 5,
        max_demand: 10
      ],
      processors: [
        default: [
          concurrency: 20,
          max_demand: 10
        ]
      ]
    )
  end

  @impl Broadway
  def handle_message(_, message, _) do
    data = Jason.decode!(message.data)

    # Simulate real work: DB + external API
    Process.sleep(Enum.random(50..200))  # fake I/O latency

    IO.inspect({self(), data["id"] || data}, label: "Processed message")

    message
  end

  @impl Broadway
  def handle_failed(messages, _context) do
    IO.puts("Failed messages: #{length(messages)}")
    messages
  end
end
----

===== Step 5: Add to supervision tree (lib/sqs++_++processor/application.ex)

[source,elixir]
----
children = [
  {SqsProcessor.Processor, []}
]

opts = [strategy: :one_for_one, name: SqsProcessor.Supervisor]
Supervisor.start_link(children, opts)
----

===== Step 6: Create the queue in LocalStack

In one terminal, ensure LocalStack is running:

[source,bash]
----
localstack start -d  # or docker run if using container
----

Then create the queue:

[source,bash]
----
aws --endpoint-url=http://localhost:4566 sqs create-queue --queue-name my-test-queue
----

You should see:

[source,json]
----
{"QueueUrl": "http://localhost:4566/000000000000/my-test-queue"}
----

===== Step 7: Run it!

[source,bash]
----
iex -S mix
----

You won’t see anything yet — because the queue is empty and long polling
is waiting.

===== Step 8: Send test messages

In another terminal:

[source,bash]
----
for i in {1..100}; do
  aws --endpoint-url=http://localhost:4566 sqs send-message \
    --queue-url http://localhost:4566/000000000000/my-test-queue \
    --message-body "{\"id\": $i, \"task\": \"do_something\"}"
done
----

You should immediately see messages being processed in your IEx session!

==== Phase 2: Early Load Testing (Highly Recommended)

Now that you have a working pipeline, let’s add simple load generation
and measurement.

===== Option A: Simple script with `aws sqs send-message-batch`

Create a quick load generator:

[source,bash]
----
# load_test.sh
#!/bin/bash

QUEUE_URL="http://localhost:4566/000000000000/my-test-queue"

for ((i=1; i<=10000; i+=10)); do
  # Generate 10 messages at a time
  entries=$(jq -n --argjson start $i '[range(0;10)] | map({Id: "\(. + $start|tostring)", MessageBody: "{\"id\": \(. + $start), \"task\": \"work\"}"})')

  aws --endpoint-url=http://localhost:4566 sqs send-message-batch \
    --queue-url $QUEUE_URL \
    --entries "$entries" > /dev/null

  echo "Sent up to $((i+9))"
done
----

Make executable: `chmod {plus}x load++_++test.sh`

This will flood ~10,000 messages quickly.

===== Option B: Use a proper load tool (better)

Install `artillery` (great for this):

[source,bash]
----
npm install -g artillery
----

Create `load.yml`:

[source,yaml]
----
config:
  target: "http://localhost:4566"
  phases:
    - duration: 60
      arrivalRate: 100    # 100 messages/sec
    - duration: 30
      rampTo: 500         # ramp to 500/sec
      arrivalRate: 500

scenarios:
  - name: "Enqueue messages"
    flow:
      - post:
          url: "/000000000000/my-test-queue"
          headers:
            "X-Amz-Target": "AmazonSQS.SendMessage"
            "Content-Type": "application/x-amz-json-1.0"
          json:
            Action: "SendMessage"
            MessageBody: '{"id": "{{ $randomInt(1,1000000) }}", "task": "load"}'
----

This is more advanced — but Artillery can simulate realistic rates.

For simplicity, start with the bash script.

===== Observe performance

While load runs, in IEx:

* Watch how fast messages disappear:
`aws --endpoint-url=http://localhost:4566 sqs get-queue-attributes --queue-url ... --attribute-names ApproximateNumberOfMessages`
* Use `:observer.start()` to see process count, memory, scheduler
utilization
* Add simple telemetry later for msgs/sec

==== Next Tuning Experiments (Fun Part!)

Once baseline works, try changing:

* `producer.concurrency: 1 → 10 → 20`
* `processors.concurrency: 10 → 50 → 200`
* `max++_++demand: 1 → 10`
* Remove `Process.sleep` → see max polling rate
* Add multiple queues and multiple Broadway instances

You’ll quickly see how BEAM handles thousands of concurrent messages
with tiny memory footprint.
